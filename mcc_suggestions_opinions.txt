# 二、我反而发现了一个非常值得你们优先尝试的「组合遗漏」

这是我看源码以后最想提醒你们的一点。

当前：

```fortran
SUBROUTINE mp_assemble_f2csum
```

已经做了一件很漂亮的优化：

> **不再先形成完整 `Sum` 临时数组，再读出来 pack；而是直接把 fine-grid block sum 累加进 MPI send buffer。**

源码自己的注释就是：

```fortran
Complete donor blocks are summed directly into the MPI send buffer
...
skipping the intermediate Sum array write and re-read
```

这其实已经非常像你说的 **FlashAttention 思想**了。

不是数学公式变了，而是：

```text
旧：
计算 Sum
↓
写内存
↓
再读 Sum
↓
pack
↓
MPI

现在：
计算
↓
直接进入 MPI send buffer
↓
MPI
```

这就是“减少 materialization / memory traffic / 中间结果”的 CPU/HPC 版本。

**但是后面通信现在仍然是：**

```fortran
CALL mpi_alltoallv(...)
```

而你们当前同一个 `distribute.F` 里已经有：

```fortran
mp_sparse_exchange(...)
```

并且 `contact3d` 已经在用它。

更有意思的是，我查了你们自己的实验记录：

`Local_Lab/experiments/sparse-peer-f2c-rerun.md`

你们**实际上已经单独测试过**把 F2C 变成 sparse peer communication：

```text
Grid2 r49: -8.2% ~ -10.1%
Grid2 r55: -7.6% ~ -7.8%
Grid2 r39: -3.8% ~ -4.2%
RMSE=0 / max_abs=0
```

而当前代码看起来保留了：

> **direct-pack F2C**

但没有把：

> **sparse-peer F2C**

组合到这个 `mp_assemble_f2csum` 中。

### 所以我目前最推荐你们检查的是：

> **能不能把“direct pack F2C”和已经验证过的“sparse-peer F2C”真正组合到当前最终分支里。**

这个方向非常漂亮，因为它不是拍脑袋的新算法。

两个 component **你们都分别验证过 bitwise identical**。

而且官方 ROMS #735 本来就在强调同一个事实：对这种 nesting assemble，低层的 `MPI_Irecv/MPI_Isend` 在普通 OpenMPI 环境下可能比高层 collective 更快；官方当年的测试里，相比 Allreduce 大约快 1–3%，相比 Allgather 大约快 6–9%，当然收益依赖机器和 MPI 实现。

### 所以我不推荐

# 六、第三个想法：有没有 ROMS 版 FlashAttention？

答案是：

**有这种优化思想，而且你们实际上已经在做了。**

但不会存在一个：

```text
flash_roms()
```

一换就快 2×。

FlashAttention真正值得借鉴的不是 Attention，而是这几个原则：

```text
减少内存读写
减少中间数组 materialization
循环融合
缓存不变量
批量处理
通信直接进入最终 buffer
尽量避免同步
```

而你们当前代码里已经有很多一模一样的思想：

```text
FlashAttention                    你们 ROMS
──────────────────────────────────────────────
不保存完整 attention matrix      不形成完整 Sum 临时场
tile 内直接累积                  fine2coarse block 内直接累加
写最终 output / buffer           直接写 MPI send buffer
复用 online 状态                 cache route plan / block map
避免重复计算                     reuse vertical factorization
合并 kernel                       batch boundary reductions
```

所以：

> **你从 vLLM 学到的思维方式完全可以迁移到 ROMS；只是优化对象从 HBM/GPU kernel 变成 CPU cache、Fortran loop 和 MPI buffer。**

# 九、我会怎么排你们下一轮实验优先级

如果我是你们现在负责 performance 的人，我不会再同时开十条线，而是按下面顺序做：

1. **P0：检查 sparse-peer F2C 是否漏合入当前最终分支。** 当前 `mp_assemble_f2csum` 已 direct-pack，但仍然 `MPI_Alltoallv`；把你们已经 bitwise 验证过的 sparse-peer F2C 和 direct-pack 组合起来。我认为这是目前“收益证据最充分 + 风险最低”的点。

2. **P0：把 r49 再细分 caller。** 现在 Grid1≈187 s、Grid2≈191 s，但 `r49` 把很多 `mp_assemble` 混在一起。不要继续盲目优化 `r49` 本身，而是搞清楚剩下 190 s 是 `get_contact3d`、F2C、boundary、crossing 中哪一类。现在是时候从“MPI hotspot”下降到“具体调用路径 hotspot”了。

3. **P1：做 rank→node→tile topology 实验。** 不要拆 Grid1/Grid2，而是固定 `96 ranks / 24ppn`，打印映射，然后测试明确的 rank binding 和几个 tile shape。尤其观察 `r40/r41/r42`。`r41 imbalance >2` 让我认为这个实验值得做，而且几乎不碰数值代码。

4. **P1：优化 Grid2 `r54 put_refine3d`。** 重点不是改插值公式，而是 invariant hoist、数据布局、loop ordering、减少 repeated load。185 s 的规模值得单独 profile。

5. **P1：继续攻 `r35 tracer_corrector`。** 现在它是 442 s 的纯计算大头。建议打开 Intel compiler vectorization report，先找“为什么哪些 loop 没 vectorize”，再写代码，不要凭感觉展开循环。

6. **P2：wet-column fast path。** 先只在 biology 等纯 local kernel 上实验 `rmask==0 → skip whole water column`。同时统计每 rank wet-cell count，与 r15/r35/r19 wall 做相关性。只有真的显示明显相关，才进一步研究 wet-aware decomposition。

7. **P2：静态通信 plan 的 persistent MPI request。** 你们现在 route plan、peer set 都已经 cache 了，但每次 sparse exchange 仍会重新 `Irecv/Isend/Waitall`。如果通信拓扑长期不变，可以研究 `MPI_Send_init/MPI_Recv_init + Startall` 缓存 request。这个更像榨最后 1%～2%，不是第一优先级。

# 十、有几个方向我反而建议暂时不要花很多时间

**第一，不要做“全 ROMS wet-point sparse representation”。** 太侵入，结构 stencil、C-grid 和 halo 都会被牵动。

**第二，不要拆 Grid1/Grid2 到不同节点。** 当前并行架构不是 grid-level rank partition，改 communicator 属于架构级重构。

**第三，不要现在急着 single precision / fast-math。** 你们现在最宝贵的资产就是 `RMSE=0/max_abs=0`。比赛允许误差不代表应该马上花掉精度预算。除非最后所有 bitwise-safe 优化都用尽，再研究 precision tradeoff。

**第四，不要再重点搞 I/O。** 当前 Grid2 write ~15 s，Grid1 ~34 s，相比 2655 s 太小了。
